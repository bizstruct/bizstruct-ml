# ADR-0001: Архітектура ядра bizstruct-ml (core, strategies, adapters, judge)

- **Status:** Accepted
- **Date:** 2026-10-05
- **Related:** `bizstruct-domain` ADR-0009 (граф і консистентність), ADR-0010 (контракти генерації, D6), ADR-0011 (wire contract)

---

## Context

`bizstruct-ml` переписано поверх `bizstruct-domain` (спершу v0.15.0, з PR E — v0.16.0). Старі блоки, `ProjectState`, `QueueMessage`, `HookPayload` і `PubSubEvent` видалено; форми повідомлень тепер належать домену (ADR-0011). Одиниця роботи — **рядок етапу** (`StageRow`): be створює рядки й статуси, ml генерує артефакти рядка, перевіряє їх на узгодженість і повертає `StageResult`. ml **ніколи не пише статуси**; переходи стейт-машини застосовує лише be, він же публікує `StageEvent`.

Транспорт лишається чергою Azure Service Bus; HTTP-сервісу немає.

## Decision

### Три шари: core, strategies, adapters

- **`core/`** — не знає про черги, HTTP і Service Bus. `stage_runner.py` виконує рядок (`run(row, snapshot_closure, language) -> RunOutcome`): збирає контекст з `row.refs`, генерує за контрактом генерації етапу (`GENERATION_CONTRACTS`), конвертує через `X.from_generated` з ідентифікаторами `derive_artifact_id`, перевіряє узгодженість і повторює. `context.py` збирає артефакти за `refs` і входи правил (`RuleInput`, домен 0.16.0, ADR-0012): вхід називає **тип артефакту** (`artifact`) і кратність `ONE` / `MANY` / `EACH` / `FINAL`. `gather_inputs` збирає **кандидатів за типом** і передає їх чистій функції домену `bind_inputs` (помилка `InputBindingError` стає `ContextError`); логіки кратностей у ml немає. Кандидати для `ONE` — власні артефакти свіжого рядка цього типу плюс артефакти рядків прямих `refs`; **якщо їх немає** і `refs` не називають жодного етапу-власника типу, діє те саме правило, що для інших кратностей: `DONE`-рядки етапів-власників із замикання (так `patterns` читається з рядка циклу, чиї `refs` називають лише рядок канви); якщо `refs` називають етап-власник, але рядок відсутній, не `DONE` або без артефактів, — `ContextError`; кілька кандидатів лишаються помилкою неоднозначності. Кандидати для `MANY`, `EACH`, `FINAL` — власні артефакти свіжого рядка плюс, для **кожного етапу-власника** типу (`ARTIFACT_HOLDERS`; канва живе в рядках `canvas` (v1) і `swot_errc_cycle` (v2..5)): екземпляри рядків, названих у `refs` під цим етапом (кожен рядок має існувати, бути `DONE` і мати артефакти, інакше `ContextError`; групу задають `refs` рядка), інакше екземпляри `DONE`-рядків цього етапу із замикання (свіжий рядок виключено); для `FINAL` так само збираються `Swot` циклу. `EACH` розгортається у виклик правила (або судді) на кожен екземпляр. Тип визначає клас моделі, а не анотація параметра правила. `consistency.py` виконує детерміновані правила й judge-чеки, застосовні до свіжого рядка, і будує підсумковий `ConsistencyReport`.
- **`strategies/`** — спосіб обходу графа. Зараз лише `pipeline.py`: `handle_message(message, backend, runner) -> Disposition`. Агентна стратегія додасться поруч, не змінюючи `core/`. Стратегія повертає `Disposition` (`complete`/`dead_letter`/`abandon`), а не торкається черги.
- **`adapters/`** — межа зі світом: `consumer.py` (Service Bus, розбір `QueueMessage`, виконання `Disposition`) і `backend_client.py` (`GET /api/internal/projects/{id}?row=<row_id>` → `ProjectSnapshot`; `POST /api/internal/hook` зі `StageResult`; шлях і автентифікація — як раніше).

Генератори етапів — підкласи `StageGenerator` (промпт + конвертація в збережені моделі), реєструються в `strategies/pipeline.STAGE_GENERATORS`. Етап без генератора завершується в dead-letter з причиною `NoGenerator`. `StageRunner` відмовляється реєструвати звичайний генератор етапу, що не має рівно одного контракту; етап з кількома контрактами (`swot_errc_cycle` має два) реєструється лише як `LoopGenerator` з точно його контрактами.

### Id артефактів виводить ml

`derive_artifact_id(row.id, ArtifactType, index)` (uuid5). Перегенерація рядка дає ті самі id, тож зовнішні ключі нижчих етапів лишаються чинними, а повторна доставка ідемпотентна без координації з be. LLM id не пише. Перед відправленням кожен артефакт проходить `parse_artifact`, тобто ml перевіряє те саме, що перевірить be: невалідний артефакт — збій генерації в ml, а не `422` і dead-letter.

### Judge: два шари і guard родини моделей

1. **`JudgeModel`** (ABC; `family: ClassVar[str]`; `complete_json(system, user, temperature)`) — рівень провайдера. Новий провайдер — один клас і один запис у реєстрі `judge/factory.PROVIDERS`; вибір — змінною `JUDGE_PROVIDER`. Реалізації: `AzureFoundryChatJudge` (`family = "mistral"`, chat completions через OpenAI-сумісний клієнт), `FakeJudgeModel` (тести).
2. **`ConsistencyJudge`** — рівень протоколу, однаковий для всіх провайдерів: системний промпт = `JudgeCheck.instruction` + фіксований розділ формату виводу; користувацький промпт = входи як JSON, підписані етапом `RuleInput`; відповідь розбирається `ConsistencyReport.model_validate_json`; на невалідну відповідь або помилку провайдера — повтор (спільний `llm/retry.py`), далі `JudgeUnavailable`. Розібраний звіт приземлюється на реальні дані: `rule_id` кожного порушення примусово дорівнює `check.id`; цитовані `artifact_ids`, яких немає серед наданих входів, відкидаються; якщо не лишилось жодного — порушення цитує id усіх наданих входів, що його мають; якщо жоден вхід id не має (наприклад, лише `Brief`) — порушення відкидається й логується (оцінка судді лишається).

**Guard.** `assert_different_family(generator_family, judge_family)` викликається при старті (`build_runner`); воркер **не стартує**, якщо родини збігаються (генератор — `openai`) або конфігурація judge неповна чи називає невідомого провайдера. Судити модель тією ж родиною означає ділити з нею сліпі зони.

Judge і генератор — окремі деплойменти й ключі (`JUDGE_*` проти `AZURE_OPENAI_*`). JSON mode (`response_format=json_object`) і `max_tokens` для judge вимкнені за замовчуванням і вмикаються лише після живого прогону `scripts/judge_smoke.py`, який перевіряє, що саме приймає деплоймент.

### Повтори узгодженості всередині повідомлення

Після генерації ml виконує детерміновані правила. Якщо є порушення `error`, ml **до 2 разів** перегенерує рядок, додаючи тексти порушень до промпту; попередження ніколи не запускають повтор; be повторів не бачить, лише фінальний звіт (ADR-0011 Q7). Після вичерпання повторів рядок усе одно повертається зі звітом, що містить помилки (be переведе його в `AWAITING_DECISION`). Judge-чеки виконуються **один раз** на фінальних артефактах, після циклу: вони дорадчі й не запускають повторів, тож їхні виклики не множаться разом із перегенераціями.

Оцінка звіту: лише детерміновані правила — `5`, якщо порушень немає, інакше `clamp(5 − кількість порушень error, 1, 5)`; з judge — `min(оцінка judge, детермінована оцінка)`. Якщо judge недоступний, до звіту додається попередження `judge_unavailable:<check_id>`, а етап усе одно завершується успіхом.

### Перевірка тексту на виродження

Після `generate_structured` і до `to_artifacts` runner виконує `validation/degenerate_text.validate_block_text` над виходом LLM, за контрактом генерації етапу й мовою знімка. Знахідка `retry_worthy` (чужа мова, заборонене письмо, повтори) повторює генерацію як помилку схеми, а коли повтори вичерпано — рядок завершується `GENERATION_FAILED`; усі знахідки йдуть у span `validate_text`. Поля, що не є прозою (`channel_type`, `relationship_type`, `breakeven_formula`, `title`), виключено з перевірки мови; імена з великої літери й короткі аліаси сегментів і так нейтральні.

### Версії промптів

Кожен модуль промпту має `PROMPT_VERSION`, а `StageGenerator.prompt_version` його віддзеркалює. Версію записано в метадані трасування (корінь трасування: `metadata.prompt_version` і тег `prompt:<версія>`; span `llm_call`: `metadata.prompt_version`), щоб результат можна було пов'язати з текстом промпту, який його створив. Правило: змінюєш текст промпту — підвищуєш версію. `1` — текст, злитий у PR #5; `2` — `empathy_map` (жорстка межа `says_and_does` / `thinks_and_feels`) і `customer_scenario` (список сегментів проєкту з позначкою сегмента цього рядка, сувора вимога до `interdependence_signal`). `patterns` і `canvas` починаються з `1`.

### Judge дорадчий

Константа `JUDGE_BLOCKING = False` (`judge/base.py`): знахідки judge обмежуються рівнем `warning` і не блокують `DONE`. Це тимчасово — до вирішення відкритого питання 5 ADR-0011 («які знахідки judge мають рівень `error`»). Тести фіксують обидва значення константи.

### Ризик: продовження блокування повідомлення

Рядок `swot_errc_cycle` у пайплайні виконується хвилинами (вимірювано: 87–129 с на 3–5 ітерацій, тобто до 14 % від 900 с), а `AutoLockRenewer` раніше жорстко обмежував продовження 300 секундами в двох місцях. Тепер це `LOCK_RENEWAL_SECONDS` (за замовчуванням 900) в обох місцях. **Поведінку брокера при спливі блокування не перевірено**: чи повідомлення піде іншому споживачеві, чи завершення впаде з помилкою — це треба перевірити на реальному Service Bus. `attempt_id` робить повторну доставку безпечною (застарілий результат дає `409`, ml завершує повідомлення), але не прибирає зайвої роботи. Значення 900 — припущення, а не вимір.

### Мова: авторитетна — знімок

І `ProjectSnapshot.language`, і `QueueMessage.language` несуть мову проєкту. Авторитетна — **знімок**: його читає ml у цьому самому повідомленні, а `QueueMessage.language` лише копія для ранньої атрибуції (ADR-0011). Пайплайн використовує тільки `snapshot.language` — і для генерації (`StageRunner.run`, промпти, перевірка тексту), і для метаданих трасування (корінь трасування відкривається після отримання знімка). Якщо значення розходяться, поведінку визначає знімок.

### Причини завершення генерації (finish reasons)

`LLMClient` обгортає `ContentFilterFinishReasonError` і `LengthFinishReasonError` підкласами `LLMError` (`LLMContentFilterError`, `LLMLengthError`). Фільтр вмісту повторюється як інші помилки LLM (`settings.llm_max_retries + 1` спроб). Обрив за довжиною (`finish_reason = length`) повторюється **один раз** (`MAX_LENGTH_RETRIES`), далі рядок завершується `GENERATION_FAILED` з повідомленням, що називає `finish_reason=length`: той самий промпт навряд чи вмістить відповідь з третьої спроби. Причина (`stop`, `length`, `content_filter`) і використання токенів обірваної відповіді записуються в метадані span `llm_call` (`finish_reason`).

### Помилка конвертації як відгук для наступної спроби

Якщо `to_artifacts` або `parse_artifact` кидає `ValueError` (зокрема `ValidationError`), текст помилки (до 1500 символів) додається до наступного виклику LLM повідомленням «Your previous answer could not be used…». Так модель бачить, чому відповідь не підійшла (наприклад, «групи мають бути зв'язними компонентами графа»), а не просто перегенеровує наосліп. Помилки LLM-викликів і виродження тексту відгуку не дають.

### Patterns (слайс 2)

Уся логіка Patterns живе в `stages/patterns.py`, `llm/prompts/patterns.py` і `stages/patterns_validation.py`, щоб її можна було замінити, коли NetScore перейде в домен.

- **Аліаси сегментів.** Модель бачить сегменти як `S1..SN`, а не як справжні id. Нумерація — за `instance_index` рядків `empathy_map` (ADR-0011: рядок k покриває кандидата k), а не за порядком `refs` чи id. Підказка містить для кожного аліаса ім'я персони та ознаки сегмента (канал, тип відносин, ціновий рівень, сигнал взаємозалежності зі сценарію; теги епіцентру, обґрунтування й питання «what if» з ideation) і список пар, які треба оцінити. Назад аліаси перетворюються на id карт емпатії через `patterns_from_generated(segment_ids=…)`.
- **NetScore — стартова пропозиція проєкту, не з книги.** Підказка так і каже. Синергія: +1 той самий тип каналів, +1 той самий тип відносин, +1 спільний тег епіцентру, +2 сигнал взаємозалежності в будь-якому зі сценаріїв пари. Конфлікт: −2 протилежні цінові рівні (premium проти low_cost), −2 протилежні відносини з клієнтом, −2 протилежна орієнтація структури витрат. Ребро графа сумісності — `synergy + conflict >= −1`; кожна зв'язна компонента — одна канва. Один сегмент: пар немає, одна група.
- **Відкладена прогалина: тип покупця.** Четвертий доданок конфлікту методології (−1 за принципово різний тип покупця, B2C проти B2B, з несумісними каналами) **не застосовується**: у домені немає такої ознаки. Підказка наказує моделі його пропустити, тож практичний діапазон конфлікту −6..0, а не −7..0. Це знана прогалина, а не рішення.
- **Тип зв'язку групи з одного сегмента** методологія не визначає; за домовленістю — `segmented`.
- **Ідентифікатори груп** детерміновані: `uuid5(ARTIFACT_ID_NAMESPACE, f"{row.id}:group:{i}")`, де `i` — позиція групи в `Patterns.groups`. Перегенерація рядка дає ті самі id груп, тож `Canvas.group_id` і рядки канв лишаються чинними. Щоб позиція не залежала від порядку, яким модель записала групи, генератор приводить їх до канонічного порядку (групи за найнижчим аліасом, аліаси всередині групи за зростанням) до побудови id.
- **Структурна валідація на боці ml — тимчасова й ізольована** (`stages/patterns_validation.py`, лише стандартна бібліотека, жодних імпортів з пакета). Домен не може перевірити арифметику моделі, тому ml перевіряє, що відповідь структурно випливає з методу: кожна невпорядкована пара аліасів оцінена рівно раз; кожен аліас у рівно одній групі; групи дорівнюють зв'язним компонентам графа пар з `synergy + conflict >= −1`. Порушення — `ValueError` з точним повідомленням, яке йде як відгук на повтор. **Модуль має зникнути**, коли NetScore (ваги, пороги, класифікація ознак) перейде в домен: тоді домен сам обчислює оцінки й групи. Це правило пов'язане з порогом `EDGE_THRESHOLD`, який також лише пропозиція.
- **Строк рішення.** Рішення про перенесення NetScore і міток (ваги, пороги та класифікатор ознак `channel_type`/`relationship_type`, які сьогодні вільні рядки з рекомендованими значеннями) має бути ухвалене **до початку експериментів** (перший прогін `pilot`/`main`). До того `patterns_validation.py` і розділ NetScore в підказці лишаються тимчасовими, а результати прогонів, що рахують NetScore у підказці, не порівнюються з прогонами після перенесення.

### Canvas (слайс 2)

Рівень деталізації — лише розгорнута канва (elaborated canvas): усі дев'ять блоків, по 2–4 картки (`CanvasGenerated`; `errc_marker` не задається). Рядок k канви бере групу `Patterns.groups[row.instance_index]`; `refs` рядка мають збігатися з картами цієї групи, інакше `ContextError`. Конвертація: `Canvas.from_generated(id=derive_artifact_id(row.id, CANVAS, 1), group_id=…, empathy_map_ids=<карти групи>, version=1, previous_version_id=None)`.

**Ідентифікатори карток** детерміновані: `uuid5(ARTIFACT_ID_NAMESPACE, f"{canvas_id}:card:{n}")`, де `n` рахується з 0 у порядку, в якому `Canvas.from_generated` просить id (секції в порядку полів `CanvasSections`, картки по порядку). Id картки залежить лише від позиції, не від тексту, тож перегенерація канви зберігає всі зовнішні ключі (зокрема майбутні ходи ERRC, що посилаються на картки).

### Узгодженість у слайсі 2

Узагальнений механізм не змінено. Після `patterns`: детермінований `multi_sided_requires_signal` (помилка запускає повтор у ml з повідомленнями як відгуком; після вичерпання повторів рядок повертається зі звітом, що містить помилку) і дорадчий judge-чек `ideation_grounds_pattern_tags`. Після `canvas`: детермінований `canvas_group_id_is_known` і дорадчий `canvas_grounded_in_customer_insights`. Входи `MANY` збирає `gather_inputs` за правилом із розділу про `core/` (прямі `refs`, інакше замикання), тож judge канви бачить карти й сценарії лише своєї групи, а `patterns` — усі.

### Цикл `swot_errc_cycle` (слайс 3)

Один рядок на канву; `refs` = рядок цієї канви (та рядок `environment_scan`, лише коли етап увімкнено; генератора для нього ще немає, тож `Swot.environment_scan_id` лишається `None`); `instance_index` = 0. Весь цикл виконується **в одному повідомленні** і повертає один `StageResult`.

- **`LoopGenerator`** (`core/stage_runner.py`): етап із кількома контрактами сам володіє циклом (`run_loop`) і викликає сервіси runner'а для кожного виклику LLM (`LoopServices.call` / `call_checked`). Тож кожен виклик зберігає повтори на помилки LLM і схеми, відгук про помилку конвертації, правило одного повтору для `length`, перевірку виродження тексту й трасування; у метаданих span `llm_call` є `label` (`swot v2`, `errc v1`).
- **Цикл** (`stages/swot_errc_cycle.py`): від канви v1 (з рядка `canvas`): `Swot` версії k (`SwotGenerated` → `Swot`, `id = derive_artifact_id(row.id, SWOT, k)`) → `loop_should_continue(scores)` (домен) → `Errc` від версії k (`id` за `ERRC, k`, `result_canvas_id` за `CANVAS, k+1`) → канва k+1 будується **детерміновано, без LLM** (`stages/errc_apply.py`) → k+1. Повертаються `Swot` 1..K, `Errc` 1..K−1, канви 2..K. Версії `Swot` мають бути суцільними від 1 (`check_contiguous`; `final_swot` домену кидає помилку на пропуску). **Фінальну версію виводить домен** (`select_final_version`, `final_canvas`); ніякого прапорця не зберігається. Вона й ряд оцінок лише йдуть у метадані трасування (span `cycle_summary`: `final_version`, `scores`, `iterations`), щоб експерименти могли їх читати.
- **Цикл завжди робить хоча б одну ітерацію ERRC**: `loop_should_continue` повертає `True` для однієї оцінки, тож «без покращення» дає 2 `Swot`, 1 `Errc` і канву v2 з фінальною версією 1, а не один `Swot`.
- **Застосування ходів** (з логіки застосування в `bizstruct-be` до його міграції, адаптовано до `ErrcMove`): ходи йдуть по черзі; хід знаходить картку версії k за **точним** текстом `target_card_text` у `target_section`, перший збіг; `eliminate` видаляє картку; `reduce` і `raise` лишають картку (той самий `id`), **замінюють її текст на `new_text`** (повний новий текст картки; домен 0.17.0) і ставлять `errc_marker`; `create` додає картку з `new_text` і маркером `create`. Хід без збігу (текст розійшовся або картку вже видалив попередній хід) — `ValueError`, і виклик Errc повторюється з цим повідомленням як відгуком; часткового застосування немає. Картки, яких крок не торкнувся, зберігають `id`, але отримують `errc_marker = None`: маркер каже, що змінив крок, який породив цю версію, а не старші кроки. Нові картки: `uuid5(ARTIFACT_ID_NAMESPACE, f"{canvas_id}:card:{n}")`, `n` рахує нові картки кроку з 0; `previous_version_id` = попередня канва; `version = k+1`; `is_generated = False`; `group_id` і `empathy_map_ids` успадковано. Наступні ходи того самого кроку бачать картки такими, якими їх залишили попередні: картка з перепису тексту знаходиться вже за новим текстом. До 0.17.0 `reduce` і `raise` лише ставили маркер і не змінювали канву (різницю між версіями давали тільки `eliminate` і `create`; у прогонах слайсу 3 одну й ту саму картку піднімали чотири ітерації поспіль).
- **Узгодженість у циклі.** Детерміновані правила виконуються після кожного виклику Errc (`call_checked`): помилка повторює **цей виклик** з повідомленнями як відгуком (до `MAX_CONSISTENCY_RETRIES`), а не весь рядок: повторення всього циклу втричі було б надто дорогим. Залишок після повторів потрапляє у фінальний звіт, як і раніше (be переводить рядок у `AWAITING_DECISION`). Фінальний прохід: `errc_move_targets_correct_canvas_version`, `canvas_group_id_is_known` для кожної версії канви (`EACH`; `Patterns` береться із замикання за правилом `ONE`), `swot_environment_scan_reference_is_known` лише коли є скан; judge-перевірки дорадчі. Якщо ітерація провалилась після повторів, **весь рядок** провалюється з номером ітерації в повідомленні (`cycle iteration 3: ...`), часткових результатів немає; id детерміновані, тож перегенерація повторює ту саму роботу.
- **Промпти** (SWOT `PROMPT_VERSION = "2"`, ERRC `"2"`; обидва були `"1"` у слайсі 3). SWOT: кластери, 2–5 тверджень осі, 1–7 можливостей і фіксований каталог загроз кластера (21 питання; формулювання `THREAT_GLOSS` написані для цього промпту, жодне не скопійоване з книги). Сильні й слабкі сторони виводяться лише з канви. ERRC v2: правило полів для кожної дії одним рядком (`eliminate` = лише `target_card_text`; `reduce`/`raise` = `target_card_text` І `new_text`, повний новий текст картки, що конкретно виражає змінений рівень; `create` = лише `new_text`) і заборона повторювати хід на картці з маркером попереднього кроку, якщо новий текст не йде далі. SWOT v2: оцінки 1–5 можливостей і загроз прив'язано до канви (1 = немає ознак у канві, 3 = можливо, але не видно, 5 = уже видно в канві) з вимогою користуватись усім діапазоном; шкали домену й критерій зупинки не змінено. З версії 2 канви кожна картка показується з `errc_marker`, щоб модель бачила, що змінив попередній крок (golden-тест). **Прогалина:** перелік питань книги про сильні й слабкі сторони (с. 217–219) недоступний; використано лише опис квадрантів із методології.

### Storytelling, future_scenario, pitch (слайс 4)

Три етапи, **по одному рядку на канву**, `instance_index = 0`. `refs` (ADR-0011): `storytelling` = рядок циклу цієї канви; `future_scenario` = рядок циклу; `pitch` = рядок `storytelling` + рядок циклу, плюс рядки `team_info` / `business_case` лише коли етап увімкнено. Усі три читають **фінальну** канву та **фінальний** SWOT цієї канви.

- **Фінальні канва й SWOT виводяться, не зберігаються.** Один помічник `gather_final(row, rows)` у `core/context.py` збирає `RuleInput(canvas, FINAL)` і `RuleInput(swot, FINAL)` через `gather_inputs` (домен: `select_final_version` над `Swot` рядка циклу; v1 береться з рядка `canvas` через замикання, v2..v5 з рядка циклу). Усі три промпти й генератори викликають лише його; прапорця «фінальна» ніде немає. Незавершений цикл (прогалина у версіях) — `ContextError`.
- **Id та системні поля.** `id = derive_artifact_id(row.id, тип, 0)` (стабільні при перегенерації). `canvas_id` — фінальної канви, `swot_id` — фінального SWOT, `storytelling_id`, `team_info_id`, `business_case_id` — з `refs`/знімка.
- **Storytelling: перспектива, мета й формат — ПРАВИЛА ПРОЄКТУ.** Методологія (крок 10) не дає типових значень жодного з трьох полів. Значення обрав мейнтейнер: `perspective = customer`, `goal = pitching_investors`, `format = text_and_image` (іменовані константи в `stages/storytelling.py`, єдине місце). Причини: пітч орієнтований на інвесторів; історія з перспективи клієнта — природний гачок для нього; `text_and_image` — найближчий формат до текстового артефакту, а зображення не генеруються, тож поле фіксує *задуману* форму. Значення названо в промпті; будь-яке інше — помилка конвертації (`ValueError` з назвою кожного поля), виклик повторюється з цим повідомленням. Це **контрольована змінна експериментів**: у кожній конфігурації, включно з майбутнім агентом, значення однакові. Зробити їх вибором користувача — пізніше продуктове рішення, не в цьому слайсі.
- **Storytelling і правило проєкту `storytelling_references_nonempty_sections`.** `canvas_references` мають вказувати на секції, в яких у фінальній канві є картки (канва після ERRC може мати порожню секцію, бо `eliminate` видаляє картки). Промпт називає непорожні секції; якщо модель все ж посилається на порожню, детермінована перевірка домену (`bind_inputs`, без особливих випадків) дає помилку, і виклик повторюється з її повідомленням. Так само `future_scenario_references_nonempty_sections` для запитань адаптації.
- **future_scenario**: вхід — фінальна канва (+ фінальний SWOT як контекст); 2–4 драйвери невизначеності, 2–4 варіанти, запитання адаптації лише в непорожніх секціях; лише діагностика, без рекомендацій.
- **pitch**: входи — розповідь storytelling, фінальні канва й SWOT, теги патернів із замикання, `team_info` / `business_case`, коли вони є. `team_section` і `financial_analysis_section` є **лише коли відповідний рядок існує і DONE, інакше `null`**. Це сказано в промпті (два варіанти блоку); невідповідність — помилка конвертації з ясним повідомленням і повтор. Рядок, названий у `refs`, але не DONE, — `ContextError`, а не мовчазний `null`. **`business_case` ще не має генератора, тож фінансова секція поки завжди `null`** (так само `business_case_id`). `risk_analysis` має спиратися на негативні твердження осі SWOT або загрози з оцінкою ≥ 3 (те саме правило, що й judge-перевірка `pitch_risk_analysis_grounded_in_swot`); промпт дає цей перелік (`risk_candidates`).
- **Узгодженість** — через `bind_inputs`, без особливих випадків: детерміновані `storytelling_references_nonempty_sections` і `future_scenario_references_nonempty_sections` (помилка повторює виклик із повідомленнями як відгуком); judge-перевірки `pitch_risk_analysis_grounded_in_swot` і `pitch_optional_sections_grounded_in_sources` — дорадчі.
- **Промпти**: `PROMPT_VERSION = "1"` для кожного етапу. Якщо вхід не збирається однозначно (немає рівно однієї розповіді в `refs` pitch, цикл незавершений), рядок падає з `ContextError`, а не вгадує.
- **Проєкт «completed».** На фейковому бекенді `ready_rows` проводить кожну форму (одна канва, розділ на дві; з рядком `team_info` DONE і без) до DONE, а `project_status` без увімкнених необов'язкових етапів дає `completed`.

### Порушення правил полів і відгук про них

Правило «яке поле до якої дії» схема JSON виразити не може, і порушення (`new_text must be provided when action is RAISE.`) виникає не в `convert`, а під час розбору відповіді самим клієнтом (`parse` за контрактом), тобто всередині виклику LLM. Тому `_call` показує моделі й `ValueError`, що виник у виклику LLM, а не лише в конвертації: повідомлення називає дію й поле. У 18 прогонах PR G таких порушень не було (0 повторів); шлях покрито лише тестами.

### Відома межа: критерій зупинки самооцінений

Критерій зупинки циклу (зважена сума слабкостей і загроз) обчислюється з оцінок, які сама генеративна модель виставляє канві, яку сама ж щойно змінила. Це не незалежна оцінка. Виміряно (n = 3 на ідею, 18 прогонів, `docs/token-ledger.md`): частка загроз з оцінкою ≥ 3 — 96,1 % з SWOT v1 і 88,5 % з SWOT v2; прив'язка шкали зменшила насичення, але не усунула його, а ряд оцінок лишається шумним (оцінки першої версії різних прогонів однієї ідеї відрізняються до трьох разів, бо кожен прогін генерує вхідні етапи заново). Тому «остання краща версія» означає «остання версія, яку модель оцінила краще», а не «краща за незалежною мірою». Ця межа відома й свідомо прийнята до експериментів; незалежна оцінка (суддя іншої родини для порівняння версій) — окреме рішення.

### Відгук про порушення мовою промпта

Повідомлення порушень надходять із домену й називають справжні id. Генератор може перевизначити `StageGenerator.present_feedback(message, ctx, produced)` (за замовчуванням без змін). `PatternsGenerator` замінює id карт емпатії на аліаси `S1..SN`, а детерміновані id груп на `group #i (S..)`, бо модель бачила лише аліаси; хук застосовують і повтори рядка, і `call_checked`.

### Що свідомо відкладено

- **Генератори `environment_scan`, `business_case`, `team_info`** (останній рядок лише читається в pitch; у фейковому бекенді він створюється готовим).
- **Агентна стратегія** і повідомлення з кількома цілями: пайплайн надсилає рівно одну ціль, повідомлення з кількома цілями йдуть у dead-letter (`MultiTargetNotSupported`).
- **Checkpoints** і **`StageProgress`** — частина фази агента (ADR-0011, відкрите питання 2).
- **Звинувачення вищого етапу** при порушеннях: винним завжди вважається свіжий рядок.
- **`validate_model`** лишається поза контрактом (ADR-0011, відкрите питання 1).

## Consequences

- be володіє станом, ml — генерацією, перевірками й id; межа між ними — доменні моделі дроту, а не копії форм у двох репозиторіях.
- Додати етап — це підклас `StageGenerator` і запис у `STAGE_GENERATORS`; додати провайдера judge — клас і запис у `PROVIDERS`.
- Помилка конфігурації judge виявляється при старті, а не на першому повідомленні.
- Дорадчий judge означає, що поки `JUDGE_BLOCKING = False`, порушення, знайдені лише judge, не зупиняють рядок і не потрапляють до зворотного зв'язку повтору.
- Ризик спливу блокування лишається, доки не перевірено поведінку брокера.

## Alternatives considered

- **Judge у core без шару провайдера** — відхилено: протокол (промпт, розбір, повтори, обмеження рівня) однаковий для всіх моделей, а різниться лише транспорт.
- **Judge-чек у кожному раунді повторів** — відхилено: judge дорадчий, тож його дорога відповідь не змінює рішення про повтор.
- **Помилка judge як `error`-порушення** — відхилено: недоступність судді не є дефектом артефакту; попередження робить прогалину видимою, не зупиняючи етап.
- **Перевірка родини через конфігурацію (прапорець «дозволити однакову родину»)** — відхилено: guard має бути неможливо вимкнути випадково.
